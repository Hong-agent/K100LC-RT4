# RT4 解码 GEMV（int4 权重 × int8 激活，M=1..4）实测记录

文件：`kernels/gemv_int4.hip`。跑法：

```bash
sudo -A docker run --rm --user "$(id -u):$(id -g)" -e HOME=/tmp \
  --device /dev/kfd --device /dev/dri -v /opt/hyhal:/opt/hyhal:ro \
  -v "$PWD/kernels":/kernels -v "$PWD/models/Qwen3.8-27B-NVFP4/rt4":/rt:ro -w /kernels "$IMG" \
  bash -c 'source /opt/dtk/env.sh >/dev/null 2>&1; hipcc -O3 --offload-arch=gfx926 -DROWS=2 \
    -o gemv_int4 gemv_int4.hip && ./gemv_int4 model.language_model.layers.0.mlp.gate_proj.weight 4 /rt/qwen38_27b.rt4 /rt/qwen38_27b.rt4.json 30'
```

测试张量：`layers.0.mlp.gate_proj.weight` **[17408, 5120]，44.6MB int4 权重**（真实权重，不是合成数据）。

## 1. 正确性（先立住，再谈速度）

与 **double 精度的参考实现**（用同一批量化的权重/激活逐元素反量化相乘）对比：

| M | 最大绝对误差 | 最大相对误差 |
|---|---|---|
| 1 | 1.75e-07 | 2.6e-06 |
| 2 | 1.75e-07 | 2.6e-06 |
| 4 | 1.75e-07 | 1.2e-05 |

即内核实现的就是精确的 int 点积 + fp32 尺度折算，没有额外误差。

## 2. 算法要点（这条路能省掉全部反量化开销）

* RT4 的 int4 是**二进制补码**（-1 存成 0xF）。取 `u = code + 8 ∈ [0,15]`，
  这个操作等价于把每个半字节的**符号位翻过来**：`u = n ^ 8`。
  于是 `Σ code·a = Σ u·a - 8·Σa`，两侧都是合法的 int8 值，直接喂 `v_dot4_i32_i8`；
  `Σa` 由激活量化顺带算出（每组一个 int32），**内循环里没有任何类型转换**。
  （踩过的坑：漏掉 `^8` 时结果差 1.67，量级正好与 Σa 同阶。）
* nibble 打包是「低半字节 = 偶数 k」（见 docs/FORMAT.md），所以一取 4 字节：
  `lo = (w & 0x0F0F0F0F) ^ 0x08080808` 恰好是 4 个偶下标权重占满 4 个字节通道，
  `hi` 同理是奇下标。激活侧在量化阶段就按同序拆成 `ae`（偶）/`ao`（奇）两个数组，
  下标与 lo/hi 一一对应。

## 3. 速度：从 117 到 536 GB/s 的五轮（同一张量、同一 804GB/s 上限）

| 版本 | M=1 | M=4 | 关键改动 |
|---|---|---|---|
| v1：每 lane 1 个 dword、组内 4 步归约 | 304 | 164 | 第一个能跑的版本 |
| v2：4 dword 展开、4 条独立归约链 | 347 | 117 | 展开反而把 M=4 的寄存器推到 127 个 |
| v3：**每 lane 一个 uint4（32 个权重）**，组内只 2 步归约 | **529** | 288 | 归约链砍半、加载完全合并 |
| v4：warp 处理 2 行（ROWS=2） | 474 | **337** | 行间共享激活加载 |
| v5：去掉循环里的 break（让编译器做软件流水） | **536** | 332 | 边际收益 |
| **纯读探针**（同访存模式、不做计算） | **688** | **723** | 说明访存模式本身没问题 |

诊断（M=1，v2）用编译开关做消融，量化了每一块的代价：

| 配置 | GB/s |
|---|---|
| 完整 | 342 |
| 去掉组内归约（`-DNO_REDUCE`） | 477 |
| 去掉激活加载（`-DNO_ACT_LOAD`） | 376 |
| 两个都去掉 | 586 |
| 纯读探针 | 687 |

结论：**组内 shuffle 归约是头号开销**（-40%），激活加载次之（-10%），
剩下的差距是 dot4/ALU 的依赖链。

## 4. 对 100 t/s 吐字目标的含义（重要）

MTP3 一步（校验批 M=4）的账：

| 项 | 字节 | 按实测带宽 | 时间 |
|---|---|---|---|
| 主模型权重（校验批 M=4） | 13.87 GB | 332 GB/s | **41.8 ms** |
| KV @128k（q8，16 个全注意力层） | 4.30 GB | ~700 GB/s（另一个内核） | 6.1 ms |
| MTP 头 ×3（0.22GB ×3，M=1） | 0.66 GB | 536 GB/s | 1.2 ms |
| **合计** | 18.8 GB | | **≈49 ms/步 ⇒ 20.4 步/s** |

一步最多出 4 个 token，所以现在**最多约 82 t/s，到不了 100**。
要 100 t/s（即 ≥25 步/s、每步 ≤40ms）需要 **M=4 时权重带宽 ≥450GB/s**（现在 332，差 35%）。

## 5. W4A4 版（int4 激活 + `v_dot8_i32_i4`）：文件 `kernels/gemv_w4a4.hip`

动机：把激活也压到 int4，则**权重 dword 与激活 dword 都是「8 个有符号 int4」**，
直接就是 dot8 的两个源操作数——内循环里既不需要 unpack，也不需要 W4A8 的 `-8·Σa` 修正项；
而且激活按 **32 个一组**给尺度（正好等于一个 lane 一次 uint4 覆盖的 32 个权重），
权重组尺度（每 128，4 个 lane 共用）与激活子组尺度相乘即可，**内循环零 shuffle**。

| 版本 | M=1 | M=2 | M=4 | VGPR(M=1/M=4) |
|---|---|---|---|---|
| W4A8（`gemv_int4.hip`） | 536 | 482 | 332 | 31 / 54 |
| **W4A4（`gemv_w4a4.hip`）** | **566** | **526** | **390** | **22 / 44** |
| 同构纯读探针（同样 uint4、同样 2.5 次迭代） | 620 | | 692 | |

正确性：与 double 参考最大绝对误差 **1.82e-07**（同样是精确的 int 点积）。

代价（激活量化误差，相对 RMS，同一份激活数据）：
**int4/32 = 0.116~0.123，int8/128 = 0.011~0.013**——int4 激活比 int8 差约 10 倍。
可接受的理由：来源模型本身就是 NVFP4（MLP 激活 4bit、组 16），W4A4 在它的设计范围内；
但**解码路径要不要用 int4 激活，建议等 M2 阶段与 llama.cpp 的 logits/困惑度对齐后再定**。

## 6. 消融与天花板：M=4 的差距在哪

| 实验（M=4，W4A4） | 权重带宽 |
|---|---|
| 完整 | 390 |
| 去掉激活加载（`-DNO_ACT_LOAD`） | 472（激活占 18%） |
| 同构纯读探针（连 dot8 都没有） | 692 |
| ROWS=2 / ROWS=4 | 384 / 26（ROWS=4 寄存器溢出 144B） |
| 占用率 | M=1 32 wave/CU、M=4 20 wave/CU（都不是瓶颈） |

结论：**M=1 已经吃到这套访存结构上限的 91%（566/620）**，
M=4 只有 56%（390/692），差的是「4 倍 dot8 + 4 倍激活流量」。
再往上要么把权重读取改成更「平」的模式（逐行 warp 的上限就是 620~690，
之前实测的 804GB/s 是整块 grid-stride 读才有的），要么上共享内存分块 + 双缓冲。

## 7. 对 100 t/s 目标的现实账（用实测数字，不用估算）

| 阶段 | 规模 | 实测 | 时间 |
|---|---|---|---|
| 主模型权重（M=4 校验批） | 13.87 GB | 390 GB/s | 35.6 ms |
| KV @128k（q8，16 层） | 4.30 GB | ~700 GB/s（另一内核） | 6.1 ms |
| MTP 头 ×3（M=1） | 0.66 GB | 566 GB/s | 1.2 ms |
| **合计** | 18.8 GB | | **≈43 ms/步 ⇒ 23.3 步/s** |

一步最多 4 个 token：接受 2.5 个 ⇒ **约 58 t/s**；4 个全中才 93 t/s。
所以 **100 t/s 现在到不了**，需要同时满足两件事：

1. M=4 权重带宽从 390 提到 **≥600 GB/s**（同构探针上限是 692，理论上还有空间）；
2. MTP3 平均每步接受 **≥2.6 个 token**（要真正按「共享隐藏态的 MTP 链」实现，
   而不是像 llama.cpp 那样把 MTP 头当独立 draft 模型用；后者实测接受率只有 32%）。

顺带：KV 用 int4（2.15GB 而不是 4.30GB）可再省 6ms，值得一起做。

## 8. 下一步（按预期收益排序）

> **2026-09-27 备注**：下面第 1 条（解码改用 W4A4）**没有采纳**。W4A4 更快，但 int4
> 激活在 64 层上传导后误差 12~16%，会把输出糊掉；最终运行时默认走 **W4A8**
> （`k_gemv_w4a8`，解码误差 1.4%），W4A4 只保留在 `RT_ACT4=1` 的性能对照里。
> 决策与实测见 [QUALITY-FIX.md](QUALITY-FIX.md) §4。第 2~4 条仍然成立。

1. ~~**解码也改用 int4 激活 + `v_dot8_i32_i4`**（W4A4）~~（见上方备注，未采纳）。
   来源模型本身就是 NVFP4（激活也是 4bit、组 16），所以精度上站得住。
   收益：dot 指令数减半（16 条 dot8 而不是 32 条 dot4），
   激活加载从每 lane 每 token 32B 降到 8B（M=4 时激活流量是权重的 4 倍，这是大头）。
   代价：权重侧要多存一个「每组 Σcode」（int16/组，约 0.1GB，3%）。
   预期：M=4 从 332 提到 500~600。
2. **hipprof 逐 stall reason 分析**（容器里有 hipprof），确认是 L1 延迟、LDS 还是
   占用率；ROWS=4 已经因为寄存器溢出崩掉（spill 160~272B），需要按 stall 数据调参。
3. **split-K**：把一行切成 2~4 段交给不同 block，用 fp32 atomicAdd 合并，
   进一步增加并行度（每个 warp 现在只有 2.5 次迭代，延迟暴露严重）。
4. KV / SSM 状态那部分单独写内核（与权重流式互不干扰，可并行覆盖）。

## 9. 2026-09-27 更新：M=3/4 校验批用 NROW=2

MTP 上线后，GEMV 的主要场景从 M=1 变成「M=3/4 校验一批候选 token」。
把每 warp 处理的行数做成模板参数后实测（`gemv_int4.hip`，gate_proj [17408,5120]）：

| M | NROW=1 | NROW=2 | 变化 | VGPR(NROW=2) |
|---|---|---|---|---|
| 2 | 391 GB/s | 418 GB/s | +7% | 55 |
| 3 | 322 GB/s | **379 GB/s** | +18% | 59 |
| 4 | 260 GB/s | **317 GB/s** | +22% | 67 |

NROW=3/4 寄存器溢出（spill 208/272B），带宽崩到 ~20 GB/s；M=1 继续保持 NROW=1
（NROW=2 在单 token 解码反而慢）。运行时 `src/k_gemv.hip` 已按 `rows` 自动选择。

M=5/6（对应 K=4 草稿）也测了：NROW=2 只有 266/235 GB/s，读 13.87GB 权重需要 52~59ms，
比 K=3 的 36~44ms 更慢，所以默认 MTP3 不改。
