# K100_LC 上把 27B 模型跑到 1000 t/s 预填充的设计依据

目标（硬指标，用户指定）：单卡单并发，27B 模型 **预填充 1000 t/s**、**吐字 50 t/s**，长上下文尽量不掉速。

本文记录"为什么必须重写算子和框架"以及重写后的技术路线。所有数字都是本机实测，不是查表估算。

---

## 1. 结论先行

1. **llama.cpp + 海光 HIP 这条路到不了 1000 t/s，且在物理上就不可能**：它是 FP16/FP32 向量通路，本卡 FP16 打包峰值实测 33.7 TFLOPS，而 27B 稠密模型 1000 t/s 预填充需要 54.6 TFLOP/s。差 1.6 倍，不是调参能补的。
2. **这张卡有一条约 4.5 倍于 FP16 的算术通路，但只有手写算子才能用上**：`v_dot8_i32_i4`（有符号 int4 × int4，8 个乘加累加进一个 int32）实测 **75.5 TMAC/s**。这条指令在 llama.cpp 里没有任何调用点。
3. **模型是 SSM + 注意力的混合架构**，65 层里只有 17 层是真注意力（每 4 层插 1 层，加末尾 1 层），另外 48 层是 Mamba 式状态空间层，每 token 成本与上下文长度无关。长上下文的二次开销只落在 26% 的层上——这正是目标可达的根本原因。
4. 基于 int4 通路的 INT4 GEMM 已经跑通并验证正确，实测 **46.1 TMAC/s（ISA 上限的 61.0%）**，
   零精度代价；把量化分组从 128 放大到 512 可到 **52.1 TMAC/s（69.0%）**，但要拿精度换。
   按 61.0% 这一档折算，短上下文预填充 **约 1800 t/s**，32k 上下文约 1400 t/s，
   128k 约 870 t/s，256k 约 570 t/s（v1 的 50% 是 1500 / 1170 / 720 / 470）。
5. 吐字速度卡在显存带宽上：真实可用带宽实测 **804 GB/s**（此前记录的 454 GB/s 是内核写错导致的误判）。int4 权重下每 token 需搬 13.8 GB，理论上限约 58 t/s，留出余量后 50 t/s 可达。

## 2. 硬件天花板（实测）

`bench/bench_isa2.cpp`、`bench/bench_bw.cpp`，K100_LC / gfx926，120 CU @ 1270 MHz，显存 4096-bit @ 875 MHz（理论 896 GB/s），64 GB HBM，L2 8 MB。

### 2.1 算术通路

| 指令 | 精度 | 实测 | 相对 FP16 |
|---|---|---|---|
| `v_pk_fma_f16` | fp16 打包 FMA | 33.7 TFLOPS | 1.0× |
| `v_dot2_f32_f16` | fp16 点积 | 16.9 TMAC/s (33.8 TFLOPS) | 1.0× |
| `v_dot2_i32_i16` | int16 点积 | 19.0 TMAC/s | 1.1× |
| `v_dot4_i32_i8` | int8 点积 | 37.9 TMAC/s (75.8 TOPS) | 2.25× |
| **`v_dot8_i32_i4`** | **int4 点积** | **75.5 TMAC/s (151 TOPS)** | **4.5×** |

换算成指令下发率：三种整数点积都是 **9.45e12 条指令/秒**，而 `120 CU × 64 lane × 1270 MHz = 9.75e12`，即已达理论值的 **97%**。这说明 75.5 TMAC/s 就是硅片上限，没有藏着没被用上的通路。

**矩阵核心不存在。** 汇编器对 gfx926 拒绝全部 MFMA 与 WMMA 变体（`v_mfma_f32_16x16x16f16`、`_f16`、`32x32x8`、`i32_16x16x16i8`、`v_wmma_f32_16x16x16_f16` 等，报 `instruction not supported on this GPU`）。HIP 里也没有任何矩阵接口可用。所以"写算子"指的是手写点积内核，不是复用 MFMA。

### 2.2 `v_dot8_i32_i4` 语义（实测确认）

- 两个源操作数各是一个 dword，内含 **8 个有符号 int4**（−8…+7），低半字节在前。
- 目标是**一个** int32 累加器，一条指令完成 8 次乘加。
- 实测：`src0=0x76543210`、`src1=0x11111111` → `28`（=0+1+…+7）；`src0=0xFFFFFFFF`、`src1=0x11111111` → `−8`，确认为**有符号**。

### 2.3 显存带宽

| 内核 | 实测 |
|---|---|
| 128-bit 网格跨步读，block=128，16 波/CU | **804.3 GB/s（理论值 90%）** |
| `hipMemcpy` D2D | 743.4 GB/s（读+写合计） |
| 早期误测的读内核 | 454 GB/s |

控制变量后确认 **804 GB/s 是可用峰值**。此前记录里的 454 GB/s 是因为内核让每个线程连续持有 8 个 `float4`，导致同一条指令内相邻线程地址跨 128 字节，访问完全未合并。

## 3. 模型的真实结构

从 GGUF 元数据和张量表读出（`Qwen3.8-27B-UD-Q4_K_M.gguf`，866 个张量）：

- `general.architecture = qwen35`，65 层，hidden 5120，FFN 17408，24 个 Q 头 / 4 个 KV 头（GQA 6:1），head_dim 256，词表 248320，上下文 262144。
- **48 层是 SSM 层**：`ssm_alpha/beta/conv1d/dt/norm/out` 加 `attn_qkv`(5120→10240) 和 `attn_gate`(5120→6144)。
- **17 层是注意力层**：层号 3,7,11,…,63 以及第 64 层，含 `attn_q/k/v/output` 和 `q_norm/k_norm`。
- 第 64 层还有 `nextn.*`（MTP 多 token 预测头）与 `shared_head_norm`。
- 量化混合：Q5_K / Q4_K / IQ4_XS / Q6_K，整体约 4.8 bpw。

每 token 的稠密乘加量：

| 项 | MACs |
|---|---|
| SSM 层 × 48 | 48 × 383.2M = 18.39G |
| 注意力层线性部分 × 17 | 17 × 340.8M = 5.79G |
| lm_head | 1.27G |
| **合计** | **25.46G MACs/token** |
| 注意力二次项 | 17 × 12288 × C（C 为上下文长度） |

注意二次项只来自 17 层。纯 Transformer 同规模模型在相同上下文下的二次项会是这里的 **3.8 倍**。

## 4. 目标可达性

按 1000 t/s 反推所需算力（int4 通路，1 MAC = 1 次 int4 乘加）：

| 上下文 | 需要的 MAC/s | 占 75.5 TMAC/s 上限 | 按实测 38 TMAC/s 折算的预填充速度 |
|---|---|---|---|
| 短 | 25.5 TMAC/s | 34% | **约 1500 t/s** |
| 32k | 32.3 TMAC/s | 43% | 约 1170 t/s |
| 128k | 52.9 TMAC/s | 70% | 约 720 t/s |
| 256k | 80.2 TMAC/s | 106% | 约 470 t/s |

吐字侧：每 token 需搬运 26.05B 参数（48 个 SSM 层加 17 个注意力层加 lm_head，不含词嵌入表）。int4 加分组尺度约 4.25 bpw，即 13.8 GB/token。

| 带宽 | 吐字上限 |
|---|---|
| 804 GB/s（实测峰值） | 58 t/s |
| 700 GB/s（留 13% 余量） | 51 t/s |
| 当前 llama.cpp 基线（22 t/s） | 相当于只用到 375 GB/s |

**结论：两个硬指标都建立得起来**，前提是走 int4 点积加手写算子这条路。

## 5. 算子设计

### 5.1 统一精度策略

全模型统一 **W4A4**（4-bit 权重 × 4-bit 激活，int32 累加，按分组尺度回写 f32）。理由：只有 int4 通路留有足够余量；int8 dot4 在 128k 上下文就需要 70% 且无余量，fp16 更是差 1.6 倍。

量化方案：

- 权重：有符号 int4，分组尺度，组大小 128（每 128 个 K 元素一个 fp32 尺度）。
- 激活：有符号 int4，按 token 与分组 动态尺度。
- 累加：组内 int32（组内最大绝对值和 = 128×64 = 8192，离 int32 溢出极远），组间用 `fmaf(cvt_f32(acc), sa[i]*sb[j], acc_f32)` 回写。
- 精度风险由后续手段控制：权重侧用 Hadamard 旋转压离群值，敏感层（嵌入、lm_head、首尾层、注意力 QK）保留 int8。

### 5.2 核心算子：INT4 GEMM

`bench/int4_gemm2.cpp`（现役）、`bench/int4_gemm.cpp`（第一版，对照）。

第一版（50.2%）的要点：

- 每线程 8×4 输出块（TM=8, TN=4），块内 128×64，256 线程。
- 共享内存按 **K 维优先** 排列（`AsT[kd][row]`），这样线程的 8 个 A 双字是连续的，2 条 `LDS.128` 加 1 条 `LDS.128` 就能喂饱 32 条 dot8。
- 分组尺度改为 **组优先布局** `sa[ng][M]` / `sb[ng][N]`，一个 warp 读 16 个连续 float，而不是按 640 字节跨步跳。**只改这一处，吞吐就从 12% 提到 28%。**
- 双缓冲：当前 K 块在算，下一块已经在搬。

第二版的四项改动（每一项都是先测量、再定位、再改）：

1. **预取块的 STS 移到 dot8 循环之后**（+8.8%）。第一版 LDG 之后立刻 STS，
   编译器把 `s_waitcnt` 插在计算之前，全局延迟完全没有被覆盖。
2. **共享内存分片寄存器流水一级**（+6%）。每级 32 条 dot8 足以盖住 LDS 延迟；
   两级流水无额外收益。
3. **分组尺度走共享内存、搭同一条流水**（+4%）。之前是随用随取的 global 读。
4. **量化分组 QG 与流水深度解耦**（可选，见下）。int32 在全 K 上都不会溢出
   （64 × 5120 = 3.3e5 « 2^31），所以 QG 只受量化精度限制，不受累加器限制。

被测量否掉的三个方向：

- **网格顺序**：把 M 维设成快变索引（想让 ~240 个常驻块共享 B 块、改善 L2），
  实测更慢 6%。这个 kernel 不是 DRAM 带宽受限，L2 流量不是瓶颈。
- **占用率**：104 VGPR 决定 2 blocks/CU。用 `__launch_bounds__(256,3)` 硬压寄存器
  会让编译器溢出，掉到 8.5 TMAC/s。所以要更高占用率必须先把累加器数量减下来，
  而那会牺牲 LDS 复用比（TM/TN 变小 → 每 dot8 的 LDS 条数上升），得不偿失。
- **更小的块**：BM/BN = 64/64、128/32 都明显更差（34 和 25 TMAC/s）。

实测结果（`f64` 参考对照，随机抽样 400 个输出点；误差按 rms|c| 归一）：

| 形状 | v1 (QG=128) | v2 (QG=128) | v2 (QG=512) |
|---|---|---|---|
| M=512, N=4096, K=5120 | 21.5 (28%) | 24.2 (32%) | 29.4 (39%) |
| M=2048, N=17408, K=5120 | 38.0 (50%) | **46.1 (61.0%)** | **52.1 (69.0%)** |
| M=4096, N=6144, K=5120 | 38.0 (50%) | 45.7 (60.5%) | 50.8 (67.3%) |

数值正确性：最大绝对误差 1.6e-6，相对 rms|c| 为 4.5e-7（纯 f32 累加噪声）。

内核资源：104 VGPR、无寄存器溢出、占用率 2 waves/SIMD（约 25%）。

余下的差距：v2 稳定运行在「自身指令数上限的 78%」，也就是约 20% 的时间停在
LDS→dot8 的依赖延迟上；占用率 2 blocks/CU 封住了继续隐藏的能力。要再往前只有
两条路：(a) 加大寄存器块降低每 dot8 的 LDS 条数，但 TM=16/TN=4 需要 64 个 int
累加器，寄存器不够；(b) 激活与权重都改成逐行尺度，整个 K 只在最后折一次，
折叠开销几乎归零（int32 存得下），代价是精度必须靠 Hadamard 旋转找回来。

QG 的精度代价（`bench/qerr.cpp`，重尾合成数据 64×5120 × 5120×64）：

| 分组 | GEMM 相对 Frobenius 误差 |
|---|---|
| 64 | 0.249 |
| 128 | 0.329 |
| 256 | 0.411 |
| 512 | 0.503 |
| 1024 | 0.596 |

这组数字本身偏悲观（重尾随机数 + 朴素分组量化，正是设计里要靠 Hadamard 旋转解决的场景），
绝对值不能外推到真实模型，但**趋势是清晰的：分组每翻一倍，误差线性变差**。
所以 QG=512 的 +13% 速度不是免费的，在真实权重的困惑度验证之前默认用 QG=128。

### 5.3 还需要实现的算子

| 算子 | 说明 |
|---|---|
| INT4 GEMV | 吐字路径，带宽受限，重点是把 804 GB/s 打满 |
| 分组尺度卷积与逐元素 | SSM 的 conv1d、alpha/beta/dt 投影 |
| SSM 扫描 | 分块并行扫描，层内每 token O(1)，无 KV cache |
| INT4/INT8 FlashAttention | 只用在 17 个注意力层；长上下文需要块稀疏来压二次项 |
| RMSNorm / RoPE / SiLU | 元素级，融合进相邻算子避免多趟读写 |
| KV cache 量化 | 17 层 × 4 KV 头 × 256 dim，256k 上下文的显存占用 |

## 6. 路线图

1. ~~**内核吞吐**：把 INT4 GEMM 从 50% 推到 65–75%~~ → 已完成：零精度代价 61.0%，
   QG=512 时 69.0%。下一步（如果要继续压）是「逐行尺度 + 只在最后折叠」那条路线，
   它的天花板接近指令数上限（~86%），但和精度问题绑在一起，应当和下一项一起做。
2. **精度验证**：用真实权重跑端到端，对比 fp16 基线的困惑度，确定分组大小（QG 现在已经
   是个免费的性能旋钮，但要用精度换）、旋转是否需要、哪些层必须保 int8。这是风险最高的一步。
3. **推理框架**：张量容器、图执行、内存池、算子库、事件级调度、双格式权重（预填充与吐字共用 int4 格式）。
   注意 M 小的形状（512 token 的预填充）现在只有 ~32% 上限，块数铺不满 120 CU，
   需要 split-K 或持久化内核，这一项进框架层时必须一起解决。
4. **长上下文**：块稀疏注意力加 KV 量化，把 256k 从约 470 t/s 拉回 1000 附近。
5. **服务层**：OpenAI 兼容 HTTP 接口，替换现在的 llama-server。

## 7. 复现方式

本项目的基准都在仓库自己的 `bench/` 下，通过 DTK 容器运行：开发机不装 DTK 工具链，
一切都进容器编译。完整步骤见 [../REPRODUCE.md](../REPRODUCE.md)，
历史进展见 [../RESUME.md](../RESUME.md)。

```bash
cd K100LC-RT4
ls bench/                  # roofline 探针源码：bench_isa2（指令吞吐）/ bench_bw（带宽）/ int4_gemm2（GEMM）
# 用 scripts/dsh.sh 进容器编译并运行，例如：
bash scripts/dsh.sh 'hipcc -O3 --offload-arch=gfx926 bench/bench_isa2.cpp -o /tmp/b && /tmp/b'
```

三个新增文件需要在同一容器里单独编译：

| 文件 | 用途 |
|---|---|
| `bench_isa2.cpp` | int4/int8/int16/fp16 点积上限与 `v_dot8_i32_i4` 语义 |
| `bench_bw.cpp` | 真实显存带宽 |
| `int4_gemm.cpp` | INT4 GEMM 第一版（正确性 + 吞吐，50.2%） |
| `int4_gemm2.cpp` | INT4 GEMM 现役版（61.0%，`-DQG=` 可切分组） |
| `x_int4/x2_int4/x3_int4.cpp` | 三轮提速的 A/B 实验台，保留作测量记录 |
| `qerr.cpp` | 量化分组 vs 精度（纯 CPU，`g++ -O2 -o qerr qerr.cpp`） |

`int4_gemm.cpp` 支持两个开关：

- `-DGD=16`（默认）或 `-DGD=32`：每个流水级的 K 跨度，实测 16 更快。
- 命令行参数 `M N K`，例如 `./int4_gemm 2048 17408 5120`。

`int4_gemm2.cpp`：

- `-DQG=128`（默认）/ `256` / `512` / `1024`：量化分组，越大越快、越不准。
- 命令行参数 `M N K`，例如 `./int4_gemm2 2048 17408 5120`。
