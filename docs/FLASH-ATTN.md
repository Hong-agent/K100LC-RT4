# 预填充 int4 FlashAttention（128k 上下文）实测记录

文件：`kernels/flash_attn_int4.hip`。跑法：

```bash
bash scripts/run_fa.sh                    # 正确性（3 个深度）+ 128k 目标形状吞吐
bash scripts/run_fa.sh check 130944       # 单看 128k 深度的正确性
FLAGS="-DBN=128 -DNT=512" bash scripts/run_fa.sh bench 1024
```

## 0. 为什么写它（问题定义）

`docs/FORMAT.md` 第 7 节量过：128k 上下文下预填充的算力**一半在注意力上**，
而现役通用 int4 GEMM（`bench/int4_gemm2.cpp`）打注意力形状
（M=1000 N=131072 K=256，K 就是 head_dim）只有 **18.66 TMAC/s = dot8 上限的 24.7%**，
折算预填充 519 t/s。窄 K（256）让 K 方向的两级流水完全摊不开，这是根因。

所以本内核改成：**一个 block 负责一个 q 头 × 64 行 query，head_dim 256 整个放在内层，
Q 块常驻共享内存，外层沿 key 方向长流水（online softmax）**。

## 1. 算法与三个关键设计

```
每个 KV tile（BN 个 key）：
  QK^T : S[BM,BN] = Q·K^T          dot8，Q/K 都是 int4，沿 d 每 128 一组尺度
  软最大: 行最大/行和走 warp shuffle；P = round(7·exp2(S − m_tile))，存成 int4
  PV   : O += P·V                  dot8，P/V 都是 int4，沿 key 分组（= 一个 tile）
```

1. **共享内存按 K 维优先排**（`KsT[kd][j]`），线程的 TM/TN 个源操作数都是连续 dword
   → 一条 `LDS.64/128` 喂多条 dot8。这是 `int4_gemm2.cpp` 那轮测出来的教训。
2. **Q 块常驻共享；K/V 走「全局→寄存器→STS」两级流水**，LDG 的延迟被同一个 tile 的
   QK 计算盖住；每个 tile 只有 **2 次 `__syncthreads()`**（时序见内核注释）。
3. **P 的定点尺度取「本 tile 的行最大」而不是 running max**。tile 内最大值正好映射到 7，
   不丢动态范围；tile 之间的差以 `beta = exp2(m_tile − r_new) ≤ 1` 折进 PV 的分组尺度，
   **不多花一条指令**（本来就有一个 (行,列) 的尺度乘积）。
   如果改用 running max，后段 tile 的 P 会被整体压成 0——这是 4-bit 注意力最常见的坑。

### 数据格式（本项目自己写 KV cache，所以按内核最舒服的方式存）

| 张量 | 布局 | 说明 |
|---|---|---|
| Q | `[n_q][KD] u32` + `Qsc[g][n_q]` f32 | dword 内 8 个 d 的 int4，**低半字节 = 偶数 d** |
| K | `[n_kv][KD] u32` + `Ksc[g][n_kv]` f32 | 同上，沿 d 分组（组 128） |
| V | `[n_kv/8][HD] u32` + `Vsc[tile][HD]` f32 | **转置**：dword 内 8 个 key 的 int4 |
| 输出 | `[n_q][HD]` f32 | 已除过分母 |

**V 为什么必须转置**：PV 的收缩维是 key，而 `v_dot8_i32_i4` 要求「收缩维就是打包维」，
所以 V 必须沿 key 打包。把它放到 cache 写入侧（每个 key 写一次）比放在注意力内核里
（每个 key 被约 96 个 q 块读到）便宜得多；解码路径同样吃这个布局。

## 2. 正确性（先立住）

三重对照（`/tmp/fa check <ctx>`，随机高斯 + 少量离群通道的数据）：

1. **内核 vs 算法模型**：把内核的定点算法（per-tile 行最大、beta 折叠、online 重标定）
   用 double 原样重算一遍。两者之差 = 纯 fp32 舍入。
2. **内核 vs 量化精确参考**：用同一批量化值做精确 double softmax——差值 = int4 P 的代价。
3. **内核 vs 原始 f32**：再加上 Q/K/V 量化本身的误差。

| 上下文深度 | tiles | 内核 vs 算法模型 | 内核 vs 量化精确 | 内核 vs 原始 f32 |
|---|---|---|---|---|
| 64 | 2 | 5.5e-08 | 7.7e-03 | 6.7e-01 |
| 4096 | 65 | 2.8e-06 | 2.9e-06 | — |
| 130944（128k） | 2047 | 4.2e-06 | 4.2e-06 | — |
| 目标形状 bench（132096） | 2064 | 3.0e-06 | 3.0e-06 | — |

读法：

* 第一列 5e-8~4e-6 说明**内核就是照着设计跑**（没有任何掩码/重标定/打包错误）。
* 第二列说明定点 P 的代价：长上下文只有 **4e-6**（相对 RMS）——因为 softmax 尖锐时
  P 的量化正好落在有效位里；短上下文（2 个 tile）到 7.7e-3，也仍然很小。
* 第三列 0.67 是**合成数据**的锅，不是内核的：测试数据每 997 个通道给一个 ×12 离群值，
  V 分组尺度被离群值顶到 ~5，常规值只剩 3~5 个量化格。真实激活没有这么重尾
  （源模型自己的 MLP 激活就是 4bit/组 16）。这条只做记录，不作为验收。

## 3. 吞吐：25.5 TMAC/s（dot8 上限的 33.8%）

目标形状：`n_heads=24`（GQA 6:1 → 4 个 kv 头）、`n_q=1024`、上下文 131072、
即 1024 行 query 各自看 131072 个 key。**384 个 block**，每块沿 2064 个 KV tile 流水。

```
吞吐: 65.20 ms/层  →  执行 25.49 TMAC/s (33.8% of 75.5)  有效 25.39 TMAC/s
      KV 流量 9.3 GB/s（609 MB/层）
      折算 16 层预填充 1024 token: 1.043s → 982 t/s（仅注意力部分）
内核资源：VGPR=245、溢出 0、256 线程/块、1 块/CU（4 wave）
```

（注意最后那行只是**注意力那一半**的折算；加上线性层的 0.53s 才是端到端，见第 5 节。）

### 优化过程（每一步都实测）

| 版本 | TMAC/s | 关键改动 / 发现 |
|---|---|---|
| v1（BM64/BN128/NT512，无流水） | 17.7 | 第一个跑通的版本，和通用 GEMM 的 18.66 差不多 |
| 加 LDS 软件流水（搬移写法） | 14.4 | **反而更慢**：多出的流水寄存器把 VGPR 顶到 128 上限并溢出 152B |
| 换 BM64/BN64/NT256 | 22.6 | 溢出 0、245 VGPR：**寄存器压力是当时的头号矛盾** |
| 2 级展开去掉寄存器搬移 | 22.3 | 无变化——说明编译器本来就把搬移消掉了 |
| **K 的 tile 列序交错** | **25.2** | 消除 B 操作数的 4 路 bank 冲突（下面详述） |
| V 的 tile 列序交错 | 25.5 | 同上，PV 侧收益小（PV 不是 LDS 受限） |

**bank 冲突那一笔**：内核里每个线程要「连续 8 列」的 8 个 dword，而相邻 lane 的起点
相隔 8 个 dword。按自然序存放时，一个 LDS.128 phase 的 16 个 lane 只用到 16 个 bank，
访问退化成 4 路冲突。把每组 8 列拆成两个 4 列半段、前后半行交错存放（`xcol()`），
lane 的地址间隔变成 4 个 dword，一个 phase 正好铺满 32 个 bank → **+13%**。

### 消融：两半各自花了多少

同一形状、同一份数据（`-DABL_*` 编译开关）：

| 配置 | ms/层 | 执行 TMAC/s（按整个形状的 MAC 折算） |
|---|---|---|
| 完整 | 65.2 | 25.5 (33.8%) |
| 只跑 QK + 软最大（跳过 PV） | 38.0 | 43.7 (57.9%) |
| 只跑 PV（跳过 QK） | 41.5 | 40.0 (53.0%) |
| 只跑 QK，且源操作数不来自共享内存 | 33.6 | 49.5 (65.5%) |
| BM64/BN128/NT512（寄存器溢出 148B） | 105.0 | 15.8 (21.0%) |

（这张表可以用 `bash scripts/run_fa.sh abl 1024` 原样重跑；同配置跑与跑之间约 ±2%。）

结论：

1. **寄存器压力 > LDS 带宽 > 算力**。同一份代码从 NT512（溢出）换到 NT256（不溢出），
   吞吐直接 1.6 倍——这是整个内核最敏感的一个旋钮。
2. QK 那半比 PV 那半贵（38.7 vs 41.5ms，但 QK 还背着软最大/量化/写 P）。
   去掉 LDS 后 QK 只快 13%，说明现在的瓶颈**不是共享内存带宽**，而是
   「非 dot8 指令 + 4 个 wave 盖不住的延迟」。
3. 每线程每 tile 的指令账：512 条 dot8 + 约 500 条其它（软最大 ~150、分组折叠 32、
   取数 96+48、流水/地址若干）→ **dot8 只占指令槽的 ~50%**，这就是天花板是
   0.5×75.5 ≈ 38 TMAC/s 的原因，而我们还有 1.5 倍的延迟/发射效率缺口。

## 5. 对硬指标的意义（用实测数字，不用估算）

128k 上下文、填充 1000 token（`llama-bench -d 131072 -p 1000` 的等价形状）：

| 环节 | 规模 | 实测/在册 | 时间 |
|---|---|---|---|
| 注意力（本内核） | 25.8 TMAC | 25.49 TMAC/s | 1.01 s |
| 线性层（int4_gemm2） | 26.0 TMAC | 48.60 TMAC/s | 0.53 s |
| **合计** | | | **1.54 s ⇒ 约 650 t/s** |

对比老路线（注意力走通用 GEMM）：1.38 + 0.53 = 1.92 s ⇒ 521 t/s。
**本轮把预填充的折算从 519 拉到约 650 t/s（+25%），但离 1000 t/s 还差 1.5 倍。**

要 1000 t/s 需要总预算 1.0s，即注意力 ≤0.465s ⇒ **≥55 TMAC/s（dot8 上限的 73%）**。
现在的 25.5 需要再提 2.2 倍，路径按预期收益排序：

1. **把非 dot8 指令压下去**（现在占 ~50% 的指令槽）：软最大那 ~150 条是大头——
   行最大/行和改用 16-bit 打包归约（`v_pk_max_f16` / `v_pk_add_u16`），
   P 的量化+打包用位运算一次成型；预期能把 dot8 占比推到 65~70%。
2. **提高占用率**：245 VGPR 只能 1 块/CU（4 wave）。累加器占 128 个（O 与 PV 的
   int32 各 64），是最硬的一块。可选：把 O 存成 bf16 对（省 32 个 VGPR，代价待验）、
   或者沿 head_dim 把 O 拆给两个 block（每个 block 只算 128 个 d，代价是 QK 要重复算）。
3. **split-KV**：现在 384 个 block 铺 120 个 CU 是 3.2 波，尾部损失约 6%；
   把 key 方向再切 2~4 份能把并行度和尾部损失都改善（需要 a/l 的合并步骤）。
4. **继续压 LDS**：TM=4/TN=8（每 dot8 1.5B 而不是 2.5B）在 NT=256/BN=128 上实测
   21.9（更慢）——因为寄存器又顶到 256 上限；等第 2 条把寄存器腾出来再回头做。

一句话：**这个内核把「int4 注意力能不能写对、写对之后能跑多快」这两个问题都回答完了**
（对 5e-8、33.8%），接下来是纯粹的指令密度与寄存器工程。
